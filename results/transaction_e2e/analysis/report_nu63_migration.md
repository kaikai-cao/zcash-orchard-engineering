# NU6.3 迁移交易的端到端成本（V3：Orchard V3 + Ironwood V3）

> 冻结时间：2026-11-03
> 上游：`zcash/orchard` @ `616a669d`（`0.16.0`）｜rustc 1.88.0 msvc｜i7-14700
> 对照基线：[`report_v2_1s2o.md`](report_v2_1s2o.md)（V2，1S+2O，2 Actions，3.202 s）

---

## 0. 结论

一笔 NU6.3 迁移形状的交易（Orchard V3 的 1 Spend + 1 Change，加 Ironwood V3 的 1 Output），合计 **3 个 Action、2 个独立 Bundle**，单线程 P 核证明生成合计 **5.285 s**，是 V2 的 1S+2O（2 Actions、1 Bundle、3.202 s）的 **1.65 倍**。

增量的分解（这是本轮最重要的结果，但**必须区分实测与模型外推**）：

| 项 | 性质 | 值 |
|---|---|---:|
| V2 实测（2 Actions / 1 Bundle） | 实测 | 3.2024 s |
| 多一个 Action（V2 拟合斜率 1.2920 s/Action） | 模型 | +1.292 s |
| **3 Actions 放在一个 Bundle** | **模型预测** | **4.4822 s** |
| V3 实测（3 Actions / 2 Bundles） | 实测 | 5.2847 s |
| **模型无法解释的残差** | 差值 | **+0.8025 s（相对预测 +17.9%，相对 V2 实测 +25.1%）** |

这个 +0.80 s 是**相对于线性模型外推值的残差**，不是受控实验直接测出的「拆池纯开销」。它至少混入三类成分：

1. 模型自身的误差——V2 拟合在 n=2 处的残差就有 +12.3 ms，3 个样本点外推到 n=3 本身带不确定性；
2. 第二次 `create_proof` 调用引入的固定流程开销（这是最可能的主项，但本实验没有把它单独测出来）；
3. 两个 Bundle 的工作负载不同（2 Action 的 Orchard Bundle 与 1 Action 的 Ironwood Bundle），固定/边际项的拆分方式未必与 V2 的单 Bundle 模型一致。

**本实验没有测量这 0.80 s 的内部构成**，所以不把它整块归因于某一个具体操作。

证明体积上有一个干净得多的事实：两个 Bundle 合计 12 256 B，而单 Bundle 3 Action 是 9 536 B，差 **恰好 2 720 B**，正好是一个 proof 的 BASE 常数。

## 1. V3-A：形状验收

不能只凭"1 Spend + 1 Change = 2 Actions"的算式认定结果。跨地址限制打开后，`num_actions` 的公式本身就是 **`spends + outputs`** 而不是 `max`（`BundleType::num_actions` 里明确写了这一点），所以必须回读 Builder 的 metadata。

实测（`SHAPE` 行，harness 直接打印）：

| 项 | Orchard V3 | Ironwood V3 |
|---|---|---|
| `bundle_version` | `orchard_v3` | `ironwood_v3` |
| 电路版本 | `PostNu6_3` | `PostNu6_3`（共用同一 PK） |
| `flag_byte` | **3**（`0b011`） | **7**（`0b111`） |
| spends / outputs enabled | true / true | true / true |
| `cross_address_enabled` | **false** | **true** |
| `value_balance` | **+15 000 000** | **−10 000 000** |
| Actions | **2** | **1** |
| spend 落在 action | **1** | （无真实 spend） |
| output 落在 action | **0** | 0 |

关键结论：**spend 在 action 1、change 在 action 0，两者不共享 action**。这正是 `spends + outputs = 2` 的直接证据——如果两个 Action 数只是"1+1 恰好等于 2"，那和"共享 action 后补一个填充"是无法区分的，而这两种结构的电路完全不同。

`flag_byte` 也符合预期：Orchard V3 的第 2 位是 0（协议强制），Ironwood 是 7（三位置满）。

两侧证明都通过 `verify_proof`，共用同一个 `PostNu6_3` ProvingKey。

### 1.1 三个指标必须一直分开

本轮最容易混淆的是下面三个数，它们不相等，也不可互换：

| 指标 | 值 | 含义 |
|---|---:|---|
| **Action 数** | 3（2 + 1） | Halo2 电路实例的数量 |
| **Bundle 数** | 2 | 两个不同 Pool、两套 flags / anchor / value_balance |
| **Proof 数** | **2** | 每个 Bundle 各自 `create_proof` 一次 |

也就是说「3 个 Action」**不是**「1 个覆盖 3 个 Action 的证明」。本报告所有耗时都按 Bundle 分别记录再求和，不做合并。

### 1.2 value_balance 的含义

`+15 000 000` 与 `−10 000 000` 相加是 **+5 000 000**，不为零。这**不代表构造错误**，但也**不能直接说成"就是 fee"**：

本实验只分别构造 Orchard 与 Ironwood 两个 Bundle，完全不触及外层交易（sighash、v6 编码、fee 计算都在本 crate 之外）。因此两个 Bundle 的 `value_balance` **尚未在任何外层交易中完成价值平衡**。这里的数值只用于描述 Bundle 构造结果，不代表一笔已经通过价值守恒检查的有效交易；剩下的 +5 M 在完整交易里对应什么（fee、其他 Pool、透明部分），本实验没有测到。

## 2. V3-B：证明成本

单线程 P 核，5 次重复：

| Bundle | Actions | Build | **Prove** | Sign | Verify | Proof | Bundle 编码 |
|---|---:|---:|---:|---:|---:|---:|---:|
| Orchard V3 | 2 | 12.2 ms | **3.2608 s** | 0.70 ms | 32.2 ms | 7 264 B | 9 009 B |
| Ironwood V3 | 1 | 4.5 ms | **2.0240 s** | 0.38 ms | 26.8 ms | 4 992 B | 未测（v6 编码不在本 crate） |
| **合计** | **3** | 16.7 ms | **5.2847 s** | 1.08 ms | 59.0 ms | 12 256 B | — |

8 线程（掩码 `0x5555`）：

| Bundle | Prove | 加速比 |
|---|---:|---:|
| Orchard V3（2 acts） | 0.8043 s | 4.05× |
| Ironwood V3（1 act） | 0.4794 s | 4.22× |
| 合计 | 1.2837 s | **4.12×** |

并行效率和 V2 的 2-Action（4.58×，效率 0.57）处在同一量级，说明拆池没有改变并行结构。

### 2.1 逐次分布与版本间比较

| 配置 | n | 均值 | 中位数 | σ | RSD |
|---|---:|---:|---:|---:|---:|
| V2 1S+2O（2 acts，`FixedPostNu6_2`） | 5 | 3.2024 s | 3.1890 s | 0.0250 | **0.78%** |
| Orchard V3（2 acts，`PostNu6_3`） | 5 | 3.2608 s | 3.2290 s | 0.0706 | **2.17%** |
| Ironwood V3（1 act，`PostNu6_3`） | 5 | 2.0240 s | 1.9960 s | 0.1071 | **5.29%** |
| 阶段 A 官方 bench（1 act，`FixedPostNu6_2`） | 3 | 1.9293 s | 1.9273 s | 0.0040 | **0.21%** |

逐次值：Orchard V3 = 3.229 / 3.329 / 3.344 / 3.191 / 3.211 s；Ironwood V3 = 1.940 / 2.068 / 2.188 / 1.928 / 1.996 s。

**比较口径必须是均值对均值，不能用 min 对 min。** 本轮 `PostNu6_3` 两组（2.17%、5.29%）的离散度是 V2（0.78%）的 3 倍和 7 倍，取 min 会系统性地偏向本轮——min 是极小值统计量，样本越分散，它离真值越远。下面统一用均值 + Welch t 检验。

| 对比 | 均值差 | t | df | p（双尾） | 判定 |
|---|---:|---:|---:|---:|---|
| Orchard V3 vs V2（同为 2 Actions，仅电路版本不同） | +0.0584 s（+1.82%） | 1.743 | 5.0 | ≈0.14 | 不显著 |
| Ironwood V3 vs 阶段 A bench（同为 1 Action） | +0.0947 s（+4.91%） | 1.975 | 4.0 | ≈0.12 | 不显著 |

**结论应当写成：在当前样本量（n=5、n=3）和当前测量精度下，没有检出 `PostNu6_3` 引起的单 Action proving 成本增长。** 这只表示本次实验未检出显著差异，不等于证明两个电路版本的 proving 成本完全相同——以本轮的离散度，这组样本只能排除大约 10% 以上的差异，更小的效应需要更多重复和更严的降噪才能分辨。

另需注意第二条对比的可比性有限：阶段 A 的官方 bench 是 coinbase 输出工作负载（无 Spend），fixture 与调用路径都与本 harness 不同，它只能作为量级参照，不构成严格的同条件对照。

还有一点不能反推：**K=11 不变只能说明证明域没有扩大，不能证明新增的那几行约束没有计算成本。**「固定域容量吸收了新增行的影响」是一个解释假设，要验证得靠阶段 E 的源码级计时，不是靠这里的总量。第 4 节会说明这个假设在源码里的位置。

## 3. V3-C：与 V2 的对比

| | V2 1S+2O | V3 迁移 | 变化 |
|---|---:|---:|---:|
| Actions | 2 | 3 | +1 |
| Bundles | 1 | **2** | +1 |
| Prove | 3.202 s | 5.285 s | **+65.0%** |
| Verify | 29.5 ms | 59.0 ms | +100% |
| Proof 合计 | 7 264 B | 12 256 B | +68.7% |
| Peak WS | 114.8 MiB | 114.5 MiB | 持平 |

### 3.1 增量分解（模型外推 vs 实测）

用 V2 拟合出的 `T(n) = 0.6062 + 1.2920·n`（n = 2/4/8，残差 +0.0123 / −0.0184 / +0.0061 s）：

| 项 | 计算 | 值 |
|---|---|---:|
| V2 基线（2 Actions，1 Bundle） | 实测 | 3.2024 s |
| 多一个 Action | $+1.2920$ | +1.292 s |
| 同样 3 Actions 放在**一个** Bundle 的预测值 | $0.6062 + 1.2920×3$ | **4.4822 s** |
| 实测（拆两个 Bundle） | — | **5.2847 s** |
| **模型无法解释的残差** | $5.2847 - 4.4822$ | **+0.8025 s（+17.9%）** |

相对 V2 实测，总增量是 **+2.0823 s（+65.0%）**：其中约 1.29 s 可归因于多出来的那个 Action（这是 V2 自身拟合出的边际项），剩余约 0.80 s 是模型解释不了的部分。

**这 0.80 s 不能直接叫「拆池的纯开销」。** 它至少包含三类成分，本实验没有拆开：

1. **模型误差**——V2 拟合在 n=2 处已有 +12.3 ms 残差，3 点外推到 n=3 本身带不确定性；
2. **第二次 `create_proof` 调用的固定流程**——这是最可能的主项，但没有单独测量；
3. **两个 Bundle 的工作负载不同**（2 Action 的 Orchard Bundle vs 1 Action 的 Ironwood Bundle），固定/边际的拆分是否与 V2 的单 Bundle 模型一致，未经检验。

要说清楚的是：残差在**方向上**是稳的（三次独立运行的合计值 5.2694 / 5.2847 / 5.2865 s 都高于 4.4822 s），所以「拆成两个 Bundle 比单 Bundle 更贵」这个定性结论成立；但**具体数值 0.80 s 的构成**目前是未知的。

### 3.2 证明体积：这里可以精确，但只能说明体积

| 情形 | Actions | Bundles | Proof |
|---|---:|---:|---:|
| V2 基线 | 2 | 1 | 7 264 B |
| 3 Actions 单 Bundle（按 `expected_proof_size` 计算，非实测） | 3 | 1 | 9 536 B |
| 实测：3 Actions 双 Bundle | 3 | 2 | **12 256 B** |
| 差值 | — | +1 | **+2 720 B** |

2 720 B 正是 `Proof::expected_proof_size` 的 `BASE` 常数（`BASE + PER_ACTION × n`，`BASE = 2720`）。**多一个 Bundle 就多一份 proof header，与 Action 数无关**——这一条是精确的、可复算的，因为证明大小是确定性的字节结构。

但要避免一个过强的推论：**字节上「多一份 BASE」不能反推时间上那 0.80 s 全部来自同一个固定操作。** 时间与字节在证明系统里不是线性可换算的——`BASE` 对应的那部分字节（IPA 的初始承诺与最终 opening 等）确实要在每次证明里重算，但第二次证明同时还要重新分配内存、重建多项式上下文、走一遍 transcript 初始化，这些在字节上不可见。所以 3.2 只支持「两份证明各自承担一份固定体积」，不支持对时间 0.80 s 的归因。

### 3.3 验证侧：另一个独立的线性模型

Verify 不共用 prove 的模型，它有一条**自己的**回归。用 V2 那三个点（n=2/4/8，每次重复 5/3/3 次取均值）：

| n | 2 | 4 | 8 |
|---|---:|---:|---:|
| Verify 均值 | 29.4956 ms | 36.3113 ms | 51.628 ms |

最小二乘：`Verify(n) ≈ 21.837 + 3.7088·n` ms，残差 **+0.241 / −0.361 / +0.120 ms**（最大 1.2%），R² = **0.9992**。

n=3 代回得 **32.96 ms**。注意这是 n=2 与 n=4 之间的**内插**，不是新测的点——它比 prove 那边外推到 n=3 更可信（prove 的 4.4822 s 是外推），但仍然是模型值。

对照实测：**两 Bundle 合计 59.0 ms，是两个 Bundle 分别调用 `verify_proof` 后求和的结果**（32.2 + 26.8 = 59.0 ms），不是一次调用。

59.0 ms 对单 Bundle 3 Action 的模型值 33.0 ms，比值 1.79×。这个比值比证明侧的 1.18×（5.2847 / 4.4822）更接近「固定项翻倍」，原因在截距占比：验证的截距 21.8 ms 就占 3-Action 模型值 33.0 ms 的 **66%**（n=2 时是 74%），而证明的截距只占 13.5%。固定项占比越高，多一个 Bundle 的相对代价就越大。

**这是给协议设计的直接含义**：把一次价值转移拆成两个 Pool 的 Bundle，验证方要付两次固定验证开销。在区块验证是瓶颈的场景下，这个代价和证明时间一样值得记录。同样的口径警告适用：59.0 ms 与 33.0 ms 的差是「实测对模型」，不是受控实验测出的拆池纯度代价。

## 4. 局限

1. **合成 fixture**：Spend 的 note 仍在叶子 0、空兄弟路径；Ironwood 侧没有真实 spend，anchor 用的是 `Anchor::empty_tree()`。这测的是电路与证明系统的成本，**不构成"我们构造了一笔真实链状态的主网交易"的证据**。
2. **不含交易层**：sighash、v6 交易编码、fee 计算、序列化都没有。Orchard V3 的 `encoded_bytes` 仍按 v5 时代的 Orchard 布局估算；Ironwood 的 v6 编码本 crate 没有实现，所以没报。
3. **Ironwood 的 note 版本是 V3**（V3 明文格式），与 Orchard 的 V2 不同，但两者的密文长度是否一致我**没有验证**——所以不给 Ironwood 的编码长度。
4. 只测了 1 线程和 8 线程两组，没有重铺线程矩阵；这也正是本轮的设计意图。
5. **`value_balance` 未在外层交易中平衡**：+15 M（Orchard）与 −10 M（Ironwood）合计 +5 M，不为零。本实验只分别构造两个 Bundle，不构造完整交易，因此这两个 `value_balance` **尚未在任何外层交易里完成价值平衡**。该数值只用于描述 Bundle 构造结果，不代表一笔已通过价值守恒检查的有效交易；+5 M 在完整交易里对应 fee、其他 Pool 还是透明部分，本实验没有测到，不作断言。

## 5. 下一步

Orchard 端到端实验到此收束。不再扩展 Action / 线程矩阵。

转入 `Config::configure()`，要回答的四个问题：

1. 10 个 Advice Column 各自的职责；
2. `q_orchard` 的四条核心约束分别约束什么；
3. 各 Gadget Config 如何复用列、Selector 与 Lookup；
4. `PostNu6_3` 新增的跨地址限制加了哪些约束、如何改变电路布局。

第 4 项现在有了实验对照，但要小心它的强度：实验显示 `PostNu6_3` **未检出**单 Action 证明成本的显著增长（Welch t 检验 p≈0.14，不是「相等」），而**确实**改变了 Action 的计数规则（`spends + outputs` 而非 `max`）。这两件事在源码里应该是分开的两处：前者属于「多加了几行约束但证明域没扩大」，后者属于「`BundleType::num_actions` 与跨地址标志的联动」。K=11 不变只说明证明域没有扩张，**不能**据此推出新增约束零成本——「2¹¹ 的填充吸收了新增行」是待验证的解释假设，要交给阶段 E 的源码级计时。

## 6. 冻结结论与证据强度

端到端实验到此冻结，不再扩展。三条可以带走的结论，各自标注证据等级：

| # | 结论 | 证据等级 | 不可外推的部分 |
|---|---|---|---|
| 1 | Orchard 证明成本主要由随 Action 数增长的部分构成：`T = 0.6062 + 1.2920·n` s，3 点拟合残差 ≤18 ms | **实测 + 拟合**（n=2/4/8，单线程 P 核） | 斜率 1.292 s/Action **不能**归因到具体 Gadget（Sinsemilla / ECC / Poseidon 各占多少未知）；截距 0.606 s 的构成同样未拆 |
| 2 | NU6.3 改变了 Bundle 的结构组织方式：跨地址禁用后 `num_actions = spends + outputs`，Spend 与 Change 不共享 Action，迁移形成 2 个 Bundle / 2 份 Proof | **实测**（metadata + action index 回读，非公式推导） | 只对本次 1S+1C+1O 形状验证过；未验证更多 Spend 组合 |
| 3 | 拆成两个 Bundle 会带来额外的证明与验证成本：两份 Proof 合计 12 256 B（比同 Action 数单 Bundle 多恰好 2 720 B = `BASE`），验证 59.0 ms 是单 Bundle 模型值 33.0 ms 的 1.79× | 体积 **实测+可复算**；时间 **实测对模型** | 证明侧 +0.8025 s 是模型残差，**内部构成未知**；不能整块归因于某一次固定操作 |

三条结论的适用范围：**库级 Bundle**、合成 fixture、单线程 P 核（8 线程另有数据）、Zcash v5/v6 交易编码之外。它们不构成对钱包实测性能、主网交易确认时间或完整交易体积的任何结论。
