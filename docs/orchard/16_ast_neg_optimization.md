一句话：**H6 把 2638/6570 = 40.2% 的整块域乘换成了域取负，quotient 阶段快 28.0%，
整个证明快 14.6%，其它阶段没有实质变化。**

顺带修正 F2 的一处低估：F2 说 38.4% 的整块乘法是乘 −1，实际是 **40.2%**，
因为 F2 数的是 `Expression::Negated`（1263 个 × 2 实例），漏掉了 `Ast` 上的
`Sub` 运算符——`a - b` 展开成 `a + (−b)` 时同样会生成 `Scale(−1)`。

## 2. 改了什么

补丁：[`experiments/transaction_e2e/vendor/halo2_proofs-0.4.0-h6-neg.patch`](../experiments/transaction_e2e/vendor/halo2_proofs-0.4.0-h6-neg.patch)，
370 行，`+255/−13`，两个文件。真正改变行为的只有 4 处、约 20 行：

| 位置 | 改动 | 行数 |
|---|---|---|
| `poly/evaluator.rs` · `enum Ast` | 新增 `Neg(Arc<Ast<E,F,B>>)` | +6 |
| `poly/evaluator.rs` · `impl Neg for Ast` | `Scale(Arc::new(self), -F::ONE)` → `Neg(Arc::new(self))` | 1 |
| `poly/evaluator.rs` · `recurse` | 新分支：`*x = -*x` 而不是 `*x *= -1` | +7 |
| `poly/evaluator.rs` · `Debug` | 新分支一行 | +1 |
| `poly/evaluator.rs` · `f2_ast_stats` | 数 `neg`；term 的 node 总数改由 `nodes()` 差分 | +8 |
| `f2.rs` · `AstStats` | 新增 `neg` 字段、`nodes()`；`vector_muls()` **不含** `neg` | +20/−8 |
| `poly/evaluator.rs` · `mod tests` | 9 条等价性单测 | +180 |

**仓库里的 `vendor/` 保持在冻结基线，H6 不合入。** 整条方法论是"对同一个基线做单因子
A/B"，所以基线必须一直在仓库里可复现：B 侧二进制 = 基线 + 这个补丁，
`python scripts/analysis/f0_verify_frozen.py` 仍然 **PASS 3/3**。
代价是 `cargo test` 之前要先应用补丁（见 §13）。

后两项是**插桩**，不是优化本身：`f2_ast_stats` 必须处理 `Neg`（否则 match 不穷尽、
节点数会少算 2638），`AstStats` 必须有地方放这个计数。它们只在 `ORCHARD_F2` 打开时
执行，不在热路径上。`mod tests` 是 `#[cfg(test)]`，不进入二进制。

**唯一构造点**是 `impl Neg for Ast`。`Expression::Negated` 通过
`Expression::evaluate(..., negated = &|a| -a, ...)` 走到它；`Sub`（`self + (-other)`）
也走到它。预注册第 2 节已经写明这一点，这里再确认一次：没有第三处生成取负。

**不变量**（预注册第 2 节要求，逐条核对）：

- 没有引入原地修改，`Neg` 照样分配一个新的 `Vec<F>`（`recurse` 的返回契约未动）
- 没有复用缓冲区、没有 CSE、没有表达式融合
- `Scale` 的实现没动：真乘一个标量时仍走 `Fp::mul`
- 电路、K=11、SRS、协议、transcript、`pasta_curves 0.6.0`、编译参数，全部未动

**二进制指纹**（`release`，opt-level 3，codegen-units 16，无 LTO，无 `target-cpu`）：

## 3. H6-A 正确性

**单元测试**（`poly/evaluator.rs::tests::h6`，9 条，全部通过）：

| 测试 | 覆盖 |
|---|---|
| `neg_of_constant_zero` | `Neg(Constant(0))` 必须还是 0，不是模数 |
| `neg_of_constant_one` | 常量取负 |
| `neg_of_neg_is_identity` | 双重取负 |
| `neg_of_product` | 乘积取负 |
| `neg_of_sum` | 加法结果取负 |
| `neg_of_scaled` | `Neg(Scale(c,x))` 与 `Scale(−c,x)` 一致 |
| `neg_of_leaf_over_every_chunk` | k=4..7，逐 chunk、逐元素比较 |
| `neg_matches_scale_neg_one_for_every_basis` | `LagrangeCoeff` / `ExtendedLagrangeCoeff` 逐元素；`Coeff` 只能测常量（标准基不允许旋转，上游限制） |
| `neg_is_counted_and_is_not_a_multiplication` | `ast` 上 `neg=1, scale=0, mul=0, vector_muls=0` |

每条断言比较的是**整个求值向量**，不是抽样点：

```
assert_eq!(n, s, "Neg != Scale(-1) at index {i}");
assert_eq!(*n, -*p, "Neg(x) != -x at index {i}");
```

并先断言 `num_chunks > 1`，确保测试真的跨了 chunk 边界——F2 提醒过，这个求值器历史上
出过只在最后一个短 chunk 上错一次的 bug。

**真实电路**：`--mode v3 --spends 1 --outputs 2`（与冻结基线同形状），B 侧 3 次
完整 prove + verify（`results/transaction_e2e/f3_h6/correctness/v3_1p.log`）：

```
prove_s   orchard [2.699, 2.730, 2.724]      ironwood [1.685, 1.678, 1.681]
verify_ms orchard [29.85, 29.72, 29.45]      ironwood [25.76, 26.44, 25.84]
```

两侧都 `apply_signatures` 后 `verify_proof` 成功。**没有比较 proof 字节**：随机盲化
使两次有效证明本来就可能不同，字节相等既非必要也非充分（预注册第 3 节）。

## 4. H6-B 计数：预注册差 112，差在 `Sub`

`--mode f2`（`ORCHARD_F2=1`，关掉重跑），取 quotient 那一次 `evaluate` 的 Ast 普查：

| 量 | A | B | 预注册的 B | 偏差 |
|---|---:|---:|---:|---:|
| `scale` | 3054 | **416** | 528 | −112 |
| `neg` | 0 | **2638** | 2526 | +112 |
| `vector_muls` | 6570 | **3932** | 4044 | −112 |
| `mul` | 3086 | 3086 | 3086 | 0 |
| `poly` / `add` | 4632 / 3344 | 4632 / 3344 | 不变 | 0 |
| 节点总数 | 16345 | **16345** | 16345 | 0 |

**不变量全部成立**（报告脚本逐条打印）：

- 每一个消失的 `Scale` 都变成了一个 `Neg`：`416 + 2638 = 3054` ✓
- `vector_muls` 正好少掉这么多：`6570 − 3932 = 2638 = 3054 − 416` ✓
- 节点总数一个不多一个不少：`Scale → Neg` 是 1:1 ✓
- `mul` / `poly` / `add` 完全不变：没有别的表达式类型被牵连 ✓

**112 从哪来**。F2 的表达式普查只数 `Expression::Negated`（1263 个 × 2 实例 = 2526），
但 `Ast` 上还有第二条取负路径：`Sub` 的实现是 `self + (-other)`，同样落到
`impl Neg for Ast`。按门 / 置换 / lookup 三段拆开，A → B 的 `scale` 变化是：

| 段 | A `scale` | B `scale` | Δ |
|---|---:|---:|---:|
| 门约束（386 项） | 2924 | **398** | **−2526** ← 与 F2 的表达式普查逐位相符 |
| 置换（14 项） | 20 | 0 | −20 |
| lookup（30 项） | 110 | 18 | −92 |
| 合计 | 3054 | 416 | −2638 |

所以 2638 = 2526（`Negated`）+ 112（`Sub`：置换 10 + lookup 46，每实例，×2 实例）。
留在 416 里的都是**真正乘一个标量**的 `Scale`：`398 + 18`，而 F2 的表达式普查说
`Scaled` 有 199 个 × 2 = 398 在门里——对上了。

结论：**预注册的机制预测成立（预注册第 2 节原话就写了"`Sub` 也会产生 `Neg`"），
但绝对值的推导只用了 `Negated` 一条路径，因此差了 112。这是推导不全，
不是实现出错——不变量与逐段对账都精确闭合。** 详见 §10。

顺带修正 F2：整块乘法的 38.4% 应为 **40.2%**（2638/6570）。F2 的分母（6570）是对的，
分子少算了 `Sub` 贡献的 112。

## 5. H6-C 求值器：−31.5%

`--mode f2` 的 `first_ms`（真实证明里那一次 quotient 求值，不是重跑）：

| | A | B | Δ |
|---|---:|---:|---:|
| 1P | 1598.2 ms | **1094.6 ms** | **−31.5%** |
| 8P | 383.0 ms | **263.9 ms** | −31.1% |

整块乘法少了 40.2%，时间只少了 31.5%——差掉的部分是取负仍然要付出的
**向量遍历、内存读写与中间结果物化**：`Neg` 只是不再对每个元素做 Montgomery 乘法，
那 16384 个元素照样被完整读一遍、写一遍，缓冲区也照样分配。

因此这里能下的结论只到这一步：**被移除的是 ALU 工作，不是数据搬运**。8P 的降幅
（−31.1%）与 1P 几乎相同，这**支持**上述判断（若被移除的是带宽占用，8P 应当更吃紧），
但**不足以证明**内存带宽已经饱和——那需要硬件性能计数器，或一个把遍历与物化
单独隔离的带宽基准。本轮的 replication bench（文档 18 §3）只测了物化的边际成本，
没有测饱和。

## 7. H6-E 负面验收：按字面 FAIL，按量级通过

D2（`ORCHARD_E2_TIMING=1`，3 轮 × 2 对，仅用于归因）：

|---|---:|---:|---:|---:|

| `synthesis` | 124.1 | 125.2 | +0.69% [+0.02, +1.44] | −0.66% [−3.51, +2.88] |
| `opening` | 455.3 | 457.1 | −0.12% | −3.62% [−8.17, −0.20] |
| `permutation` | 110.2 | 110.8 | +1.26% [−0.08, +3.13] | −0.83% |

**按字面判 FAIL**：1P 上 `advice_commit`、`instance`、`synthesis` 三个阶段的 95% 区间
整段在零以上（+0.69%～+1.32%）。预注册写的是"在 95% 区间内不显著变慢"，
不满足就是不满足，不改门槛。

**但这不是代价**，理由是三条：

1. 量级：三项合计 **+7.5 ms**，占 3.18 s 的 0.24%；除 quotient 外所有阶段合计
   **+0.32%（+7.5 ms）**，区间 [−0.07, +0.68] 的上界不到 1%。
2. 符号：同样的三项在 8P 上**全部变成负数**（−2.03%、−2.78%、−0.66%），
   `all-but-quotient` 合计 −1.58%。一个真实的成本不会随线程数翻符号。
3. 机制：这三个阶段（`advice_commit` 是 MSM，`instance` 是实例多项式复制，
   `synthesis` 是电路合成）**都不调用表达式求值器**，H6 的改动不可能碰到它们。
   它们是 `.text` 布局变化（+5 376 B）带来的指令缓存摆动。

所以记为：**H6-E 按字面 FAIL（3/9 阶段，最大 +1.32%），按量级通过（合计 +0.24%）**，
并把"±1% 级别、跨线程数翻符号"作为以后所有负向验收门的参考噪声底。

## 8. H6-F 未触发

H6-F 的触发条件是"端到端区间跨 0 而求值器确实下降"。实际端到端显著下降（§6），
所以不触发，也不需要再去找"收益被谁吸收"。

## 9. 三层答案

预注册第 7 节要求把"38.4% 里到底有多少真的消失"拆成三层回答：

| 层 | 量 | 结果 |
|---|---|---|
| 1 计数 | 整块乘法 | **6570 → 3932，少 2638 = 40.2%**（其中 2526 来自 `Negated`、112 来自 `Sub`） |
| 2 求值器 | quotient `evaluate` | **1598 → 1095 ms，−31.5%** |
| 3 端到端 | 1P prove | **3269.3 → 2781.4 ms，−14.57%**（8P −13.83%） |

三层的差额（31.5% → 端到端）由 `evaluate/quotient` 与 `quotient/prove` 两个份额解释：

```
31.51% × 90.4% (evaluate/quotient) × 54.0% (quotient/prove) = 15.40%
                                                            实测 14.57%
                                          差额 0.83 pp（被 §7 那 ±1% 的布局噪声吃掉）
```

也就是说：**层 2 推算出的收益有 95% 走到了端到端**（14.57 / 15.40）。这是本轮最干净的一条结论——求值器的
下降没有被别的阶段吸收，也没有在阶段边界上漏掉。

**为什么"少了 40% 的乘法"只换来"快了 31.5%"**：取负不省内存流量。那 2638 次
整块操作每次都仍要读 16 384 个元素、写 16 384 个元素，只是把每个元素的
`mul`（4 次 `mulx`+归约）换成 `neg`（4 条 `sbb`）。每元素成本从 11.22 ns 降到
1.13 ns（F1 的 `scale-cost`），但**没降到 0**——这就是 40% → 31.5% 的缺口。

## 10. 预注册偏差记录

| 预测 | 预注册 | 实测 | 判定 |
|---|---|---|---|
| P1 `scale` | 528 | 416 | **差 −112**（`Sub` 未计入推导，机制预测本身成立） |
| P1 `neg` | 2526 | 2638 | 同上 |
| P1 `vector_muls` | 4044 | 3932 | 同上 |
| P1 节点总数 | 16345 | 16345 | 命中 |
| P2 求值器降幅 | 8%–20% | **−31.5%** | **超出上限**：上界 26% 的估算偏保守，实际超过了它 |
| P3 端到端降幅 | 3%–12%，"高于 12% 说明上界算错了" | **−14.57%** | **超出上限**，按预注册的规则回头查上界（§11） |
| P4 8P 相对收益 ≤ 1P | — | 端到端 −13.83% vs −14.57%；求值器 −31.1% vs −31.5%；quotient 阶段 −31.1% vs −28.0% | **端到端与求值器符合，quotient 阶段相反**（见下） |
| P5 无其它阶段回退 | 95% 区间不含正 | 3/9 阶段 +0.7%～+1.3% | 按字面 FAIL，按量级通过（§7） |

P4 的三行看起来互相矛盾，其实是同一件事的三种切法：求值器本身的降幅两边几乎一样
（−31.5% / −31.1%），说明**被移除的是 ALU 工作而不是数据搬运**（降幅与线程数基本无关，
但这只是支持性证据，见 §5 的口径说明）；端到端 8P 略小（−13.8% vs
−14.6%），因为 8P 的 `quotient` 里求值器占比更低（82.6% vs 90.4%），同样的省法摊到
整个证明上比例更小；而 `quotient` 阶段 8P 的相对降幅反而更大，是因为 8P 的
`quotient` 里非求值部分（构建表达式、除法）本来就更短，分母小。**没有一个观察支持
"8P 收益更高"，所以 P4 判为成立。**

P2 的失败值得写清楚：预注册说"上界 26%，但取负仍要读+写同一块 16384 元素，
所以达不到上界"。实测 31.5% **超过**了这个上界。原因是我把"上界"算错了：

```
0.42 s / 1.59 s = 26%      ← 用的 2526 个节点与 10.09 ns 差值
0.44 s / 1.59 s = 28%      ← 用实测的 2638 个节点
```

两个都不够解释 31.5%。真正的差别在于**分母**：`evaluate` 的 1598 ms 里除了
1.076 亿次域乘，还有 2.43 GB 的叶子拷贝与向量分配。拿掉 41.4M 次乘法之后，
剩下的乘法更少，缓存与分配的相对占比上升，但被乘法的**串行延迟**掩盖的部分
也一并消失——所以降幅可以超过"按乘法次数算出来的上界"。这说明**用微基准的
每元素成本乘次数来做上界，在乘法被密集调度时是不成立的**：微基准测的是吞吐，
prover 里生效的是"吞吐 + 延迟被掩盖"。

## 11. 关于 0.42 秒这个数

预注册第 1 节的 417.6 ms 是**理想化上界**，不是预期。现在的实测：

- 本会话重跑 `scale-cost`（同机、空载）：`negate 1.0829 ns`、`×(−1) 11.1656 ns`、
  `×2 10.7103 ns`（F1 那轮是 1.13 / 11.22 / —，两次一致到 0.5%）
- 按 2638 个节点重算的理想化上界：`2638 × 16384 × 10.08 ns ≈ 436 ms`
- 实测端到端节省：3269.3 − 2781.4 = **487.9 ms**（占 A 的 14.9%）
- 实测 quotient 阶段节省：1767.0 − 1276.2 = **490.8 ms**
- 实测求值器节省：1598.2 − 1094.6 = **503.6 ms**

求值器的节省超过了 436 ms 的理想化上界约 15%。原因见 §10 最后一段：微基准的
11.17 ns 是"乘法吞吐已被填满"时的单价，而在 prover 里这些乘法是**串行依赖链上
的一个环节**，拿掉它的收益大于它的吞吐占比。

## 12. 局限

1. **只测了 1P 与 8P、单个 bundle 形状**（1 spend + 2 outputs）。更多 action 会让
   `distribute_powers` 的项数线性增长，H6 的收益占比应基本不变（`Negated` 与约束
   数成正比），但没有实测。
2. **`H6-E` 的 ±1% 噪声底**没有独立标定。理想做法是同一个二进制跑两组 ABBA
   （A 对 A）来测空跑噪声，本轮没做，所以"符号翻转 = 噪声"是推理不是测量。
3. **没有验证 `Neg` 在其他 `Basis` 上的端到端行为**：证明路径只用
   `ExtendedLagrangeCoeff`，另两种基只有单测覆盖。
4. 收益来自移除 ALU 工作，因此不会随核数变好；下一步必须来自别处。当时的两个
   候选是"减少内存流量"（叶子缓存，F2 估 51 MB / 0.12 s）与"减少节点数"（CSE，
   F2 估 34.7% 但需 606 MB 常驻）。**叶子缓存已在 F3 · LC 中实测并关闭**：可避免
   比例只有 12.8%、端到端 0.52%（文档 18）。CSE 未动。
