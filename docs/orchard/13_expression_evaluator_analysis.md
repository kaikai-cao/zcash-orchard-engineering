# 13 · Stage F2：表达式求值器的成本归因

> 编号说明：任务书里写的是 `12_expression_evaluator_analysis.md`，但 12 号已被 F1
> （`12_fp_mul_microbench.md`）占用，且 F1 的结论需要在这里被修正，所以本文取 13。
>
> E3 的采样给出了一个刺眼的事实：`Fp::mul` 占 prover 自采样 **33.08%**，其中 **91.8%** 的样本
> 直接挂在 `evaluator::impl$5::evaluate::recurse` 下面。采样能说"这里在乘"，说不了"为什么乘这么多次"。
> F2 不测量新工具，只做一件事：**把表达式树数清楚**，让每一个乘法都能被指认来源。
>
> 一句话结论：quotient 阶段 1.79 s 里有 **1.59 s（89.1%）是求值器在遍历表达式树**，而遍历的成本是
> **6570 次"整块乘法" × 16384 个元素 = 1.076 亿次域乘**；这些乘法里 **38.4% 是把整块乘以 −1**。
> 不是 FFT，不是 MSM，也不是递归本身有冗余。

## 1. 方法：计数，而不是再采样一次

### 1.1 为什么采样到此为止

E3 的样本只能回答"某个 PC 出现在栈上的频率"。它有三个天然边界：

1. **不能区分源级操作次数**。`recurse` 里一个 `*lhs *= *rhs` 是对**整块** `Vec<F>` 的循环，
   一条源码语句对应 4096 次 `Fp::mul`。采样看到的是"在乘"，看不到"乘了几次、为什么这么多"。
2. **不能归因到约束来源**。同一个 `recurse` 帧既可能来自门约束，也可能来自 permutation 或 lookup。
3. **不能给出上界**。33% 是"当前花了多少"，不是"理论上应该花多少"。

所以 F2 换成**结构计数**：域运算次数 = 节点数 × 多项式长度，两头都能独立核验。

### 1.2 三个插桩点（全部在 vendored 副本里，环境变量门控）

`ORCHARD_F2` 未设置时，全部逻辑退化为一次布尔判断。

| 位置 | 做什么 | 开销 |
|---|---|---|
| `plonk::keygen::keygen_vk` 末尾 → `f2::maybe_run` | 遍历 `ConstraintSystem` 的 193 条门多项式，统计节点/深度/重复子树/叶子复用/CSE 上界 | 一次性，O(7531 节点) |
| `poly::evaluator::Evaluator::evaluate` 包装层 | 统计融合树的节点构成（含 430 个顶层项逐项明细），记录 chunk 几何；随后计时一次真实求值 | 每次 O(16345 节点) |
| `plonk::prover` 的三条表达式链 → `f2::counted` | 用 `inspect` 数出门/permutation/lookup 各产出多少个 Ast 项 | 每项一个 relaxed 自增（430 次/证明） |

### 1.3 关于"计数构建 vs 计时构建"

任务书要求区分两套数据。这里做法略有不同，理由如下：

- **计数是解析式的，不是累加式的**——`f2_ast_stats` 在 `Instant::now()` **之前**跑完，
  被计时的 `evaluate_inner` 里没有任何计数器。所以**同一次运行里既有精确计数、又有无计数器的计时**，
  不需要维护第二个二进制。
- 反过来验证也做了：1P 三次独立进程 + 8P 一次，四个进程的节点计数**逐位相同**
  （16345 / 3086 / 3054 / 3344 / 4632），说明计数是确定性的结构量，不随运行波动。
- 唯一的"重复执行"是 `ORCHARD_F2_BENCH=n`：把同一个真实 `Ast` 在真实多项式上再求值 n 次，
  取中位数。这 n 次走的是同一条无计数器路径，所以它是纯粹的计时样本。

### 1.4 实验配置

与 E1/E2/E3 完全一致：PostNu6_3、2 Action（1 spend + 1 change output）、K=11、
`pasta_curves 0.6.0`、`halo2_proofs 0.4.0`（vendor）、release、绑 P-core。
独立 target 目录（`target/f2`）构建，**不覆盖** E1/E2 的基线二进制。

```
RAYON_NUM_THREADS=1 ./orchard-e2e --mode f2 --mask 0x1  --reps 3   # 1P ×3 进程
RAYON_NUM_THREADS=8 ./orchard-e2e --mode f2 --mask 0xFF --reps 3   # 8P ×1 进程
```

## 2. 表达式层：约束系统长什么样

### 2.1 节点构成

| 变体 | 数量 | 说明 |
|---|---:|---|
| `Product` | **1424** | 二项相乘，求值时是一次整块乘 |
| `Sum` | 1514 | 整块加 |
| `Scaled` | 199 | 乘以常数（非 −1） |
| `Negated` | **1263** | 取负——**求值时是一次整块乘**（见 §6.1） |
| `Fixed` 查询 | 1161 | 叶子 |
| `Advice` 查询 | 968 | 叶子 |
| `Constant` | 1002 | 常数项 |
| `Instance` / `Selector` | 0 / 0 | lookup 表走 `Fixed`；虚拟选择器已被压缩掉 |
| **合计** | **7531** | 55 个门 / 193 条门多项式 |

深度分布（按门多项式计）：深度 4:2、6:27、7:22、**8:46、9:79**、10:4、11:9、12:2、13:1、14:1。
主体集中在 8–9 层，最深的 14 层是那几条 Sinsemilla 相关的大约束。

> 这里有一个容易被忽略的换算：`Negated` 在表达式层是"取负"，在求值树里却变成
> `Scale(−1)`——因为 `Neg for Ast` 就是 `Ast::Scale(Arc::new(self), -F::ONE)`
> （`poly/evaluator.rs:352`）。所以 199 + 1263 = 1462 才是每个实例真正的整块乘法数。

### 2.2 重复：84.6% 的节点是重复子树

| 指标 | 值 |
|---|---:|
| 表达式节点总数 | 7531 |
| 互异结构子树 | **1157** |
| 重复节点 | 6374（**84.6%**） |
| 叶子查询出现次数 | 2129 |
| 互异叶子查询 | **49**（复用 43.4×） |
| CSE 可省的整块乘法 | **1002 / 1623 局部乘法**（61.8%） |

CSE 的算法是 `树的乘法数 − 该树的 DAG 乘法数`，每个节点只记自己的局部乘法
（`Product`/`Scaled` 记 1，其余记 0）。**这一点必须这样做**：若按"子树总成本 ×(份数−1)"累加，
嵌套重复会被逐层重复计入，我第一次算出的 3019 就大于该子树的乘法总数 2886——不可能，已修正。

重复的来源很具体：同一个 `q_m · a · b` 形状在多个门里反复出现，`a`、`b` 这类叶子在
一条约束里出现 2–3 次。**这不是 bug，是 ZK 约束的常态**。

## 3. 融合树：真正被求值的那棵树

### 3.1 它是怎么拼出来的

`prover.rs` 把三个来源拼成一个 `distribute_powers` 树（用 y 的幂做线性组合），然后交给求值器：

```text
per instance:  [193 条门多项式] [7 项 permutation] [15 项 lookup]
2 个 instance ⇒ [193,7,15] [193,7,15] = 430 个顶层项
```

**顺序是按 instance 分块交错的**，不是"全部门→全部 permutation→全部 lookup"。
这一点我一开始判断错了，把第一个 instance 的 permutation/lookup 算进了门里，归因表随即对不上
（2848 vs 2801）。现在三段项数由 prover 自己数出来（`f2::counted`），不再靠假设。

最终树：**16345 个节点**，最大深度 22。

| 节点 | 数量 |
|---|---:|
| `Poly` 叶子 | 4632 |
| `Mul` | 3086 |
| `Scale` | 3054 |
| `Add` | 3344 |
| `ConstantTerm` | 2198 |
| `LinearTerm` | 30 |
| `DistributePowers` | 1（430 项） |

### 3.2 一次求值 = 1.076 亿次域乘

扩展域长度 **16384**（K=11，n=2048，extended_k=14）。于是：

| 量 | 计算 | 结果 |
|---|---|---:|
| 整块乘法 | `3086 + 3054 + 430` | **6570** |
| 域乘 | 6570 × 16384 | **107,642,880** |
| 域加 | 3344 × 16384 | 54,788,096 |
| 叶子元素拷贝 | 4632 × 16384 | 75,890,688 |

**这就是"为什么这么多域乘法"的答案**：不是递归把某个乘法算了多遍，而是**树的每个乘法节点
都在一整块 16384 个元素上展开**。6570 个节点 ⇒ 1.076 亿次乘法，量级完全由
"节点数 × 扩展域长度"决定。

同时它解释了另一个容易被忽略的成本：叶子节点 4632 次，每次都要把一块 16384×32 B = 512 KB
的数据拷出来（`B::get_chunk_of_rotated`），合计 **2.43 GB** 的搬运。

### 3.3 归因：门约束占 94%，不是 lookup

| 来源 | 顶层项 | 整块乘法 | 占比 |
|---|---:|---:|---:|
| 门约束 | 386 (=193×2) | 5772 | **94.0%** |
| permutation | 14 | 126 | 2.1% |
| lookup | 30 | 242 | 3.9% |
| 合计 | 430 | 6140 | — |

校验（脚本自动执行，失败即报警）：门段的 `Mul`/`Scale` 应等于表达式层 `Product` 与
`Scaled + Negated` 的 2 倍 —— 实测 **2848 / 2924**，与期望**逐位相符**。
这说明归因不是估计，而是可对账的。

> 我最初的直觉是"lookup 的大表会产生大量 Scale"，实测把这个直觉否掉了：
> Orchard 的两个 lookup 只贡献 3.9%，因为它们的表项是 `Fixed` 叶子，代价在拷贝而不在乘法。
> **如果按直觉去优化 lookup，会打空。**

## 4. 隔离计时：这 1.59 s 里发生了什么

把 `evaluate_inner` 单独计时（同一个真实 `Ast`、真实多项式）。**先说一个测量问题**：
同一份代码在不同批次里，绝对值漂移了约 6.5%（一批 1559–1599 ms，另一批 1666–1683 ms），
这是机器热状态/频率的漂移，不是代码变化。所以下面的主口径是**同一进程内的比值**，
绝对值只作量级参考。

| 配置 | poly_len | chunk × 块数 | 首次 (ms) | 中位 (ms) | 备注 |
|---|---:|---|---:|---:|---|
| 1P（批次 B，n=3） | 16384 | 4096 × 4 | 1693.3 | 1666.0 | `--reps 3` |
| 1P（批次 B，n=3） | 16384 | 4096 × 4 | 1680.8 | 1681.2 | `--reps 3` |
| 1P（批次 B，n=3） | 16384 | 4096 × 4 | 1685.6 | 1683.2 | `--reps 3` |
| 1P（批次 A，n=3） | 16384 | 4096 × 4 | 1589.2 / 1556.4 / 1587.6 | 1565.6 / 1559.1 / 1598.6 | 同一二进制，早一批 |
| **1P（同进程对照，n=1）** | 16384 | 4096 × 4 | **1592.7** | — | `--reps 0`，同时输出 E2 阶段 |
| 8P（n=3） | 16384 | 512 × 32 | 394.6 | **391.2** | 离散 5.4% |

同进程内对照（`raw_1p_ratio.log`，`--reps 0`，避免 bench 重跑污染阶段计时）：

| 量 | 值 |
|---|---:|
| quotient 阶段（E2 计时，同一进程） | **1787.9 ms** |
| 其中求值器 `evaluate` | **1592.7 ms** |
| **占比** | **89.1%** |

剩下的 **195 ms** 才是 `vanishing::commit`（随机多项式 MSM）、表达式→`Ast` 构建、
`divide_by_vanishing_poly`（FFT）、`extended_to_coeff`（iFFT）与 h 的承诺。
**这与 E3 "FFT 子树覆盖度仅 3.01%" 的结论一致**：quotient 不是 FFT 阶段。

> 8P 的对照：求值器 1681 → 391 ms（**4.30×**），高于整证明的 3.62×。
> 说明求值器的并行效率**优于**全局，它不是在拖后腿的那一部分——拖后腿的是
> synthesis 的串行地板和 opening 的子线性。

### 4.1 成本账（这 1.6 s 花在哪）

| 项 | 数量 | 单价（F1 实测） | 时间 |
|---|---:|---:|---:|
| 域乘 | 107.6 M | 10.5 ns | 1.130 s |
| 域加 | 54.8 M | 3.42 ns | 0.187 s |
| 叶子拷贝 | 2.43 GB | ~20 GB/s | ~0.12 s |
| 小计 | | | **1.44 s** |
| 残差（16345 次 `Vec` 分配、折叠、边界检查） | | | 0.15 s（对 1593 ms 实测） |

模型解释度约 **90%**：乘、加、拷贝三项都是独立可核验的量，残差里没有藏着第四个大头。

单价用 10.5 ns 而不是 14.75 ns：后者是**依赖链延迟**，而 `recurse` 内部是 4096 个独立元素的循环，
受吞吐约束。§5 会证明这个选择是对的。

## 5. 与 E3 交叉验证：两条独立路径对上了

E3 用采样说：`Fp::mul` self 占 1P 的 **33.08%**，证明总 CPU 3.492 s ⇒ **1.155 s**。
F2 用计数说：每次求值 **1.076 亿次**域乘。

两者相除：`1.155 s / 107.6 M = **10.70 ns/次**`。

这个数字的位置本身就是结论：

| 参考 | ns/次 | 含义 |
|---|---:|---|
| F1 `thr8`（全内联、8 路 ILP） | 10.14 | 理想吞吐 |
| **反推的实测均价** | **10.70** | **比理想吞吐只高 5.5%** |
| F1 `thr_call`（未内联 + 8 路 ILP） | 12.59 | 未内联吞吐 |
| F1 `lat_call`（未内联、依赖链） | 21.73 | 延迟 |

两条完全独立的证据（采样占比 vs 结构计数）在 0.1 个百分点内吻合，
这是 F2 最重要的**方法学**结果：**计数和采样互为校验，而不是互相替代**。

## 6. 三个可量化的杠杆

### 6.1 杠杆 A：`Negated` → `Scale(−1)`（最大且最便宜）

`Neg for Ast` 的实现是 `Ast::Scale(Arc::new(self), -F::ONE)`（`poly/evaluator.rs:352`）。
于是表达式层 1263 个 `Negated`，每个都变成一次**完整的 Montgomery 乘法**——乘数是 −1。

融合树里：`Scale` 共 3054 个，其中 **2526 个来自 `Negated`（82.7%）**，
占全部 6570 次整块乘法的 **38.4%**。

实测单价（`f1-fp-mul scale-cost`，16384 元素缓冲区，200 遍 × 5 轮取中位）：

| 形态 | ns/元素 | 相对 |
|---|---:|---:|
| `*x = -*x`（取负） | **1.13** | 1.0× |
| `*x *= -1`（`Scale(−1)`） | **11.22** | **9.9×** |
| `*x *= 2`（普通常数乘） | 10.60 | 9.4× |

上限估算：

```
2526 × 16384 = 41,385,984 次域乘
×(11.22 − 1.13) ns = 0.418 s  ≈ 证明的 12.6%（按 3.3 s）
```

实现代价极小：加一个 `Ast::Neg` 变体（或在 `Neg` 里直接构造它），求值分支做 `*x = -*x`。
**这是 F2 找到的最大单项，也是唯一一个"改几行、语义不变、可证明等价"的候选。**

### 6.2 杠杆 B：CSE（有力但被内存卡住）

结构上 84.6% 的节点是重复；按 DAG 求值可省 **1002 / 1623** 的局部乘法，
融合树里约 **2004 个整块乘法（30.5%）** ≈ 0.35 s。

但代价是明确的：要让共享子树的中间结果可复用，必须在一次 chunk 求值期间**常驻**
1157 个互异子树 × chunk 大小。按整域算：

```
1157 × 16384 × 32 B = 606 MB 常驻临时量（与线程数无关，只与互异节点数有关）
```

这比现在"每个节点分配、用完即弃"的峰值高一个数量级——**全量 CSE 不可行**。
可行的变体只缓存高复用节点（例如复用 ≥ 8 次），把常驻量压到几十 MB，
预期收益按比例下降。**这一条应作为"有条件候选"，不进 F3 首选。**

### 6.3 杠杆 C：叶子缓存（便宜、确定）

4632 次叶子访问只涉及约 **100 个互异查询**（每实例 49 个），却搬了 **2.43 GB**。
把这 100 个 chunk 缓存起来：

```
100 × 16384 × 32 B = 51 MB 常驻  →  省掉约 2.3 GB 拷贝 ≈ 0.12 s（约 3.6%）
```

收益比杠杆 A 小，但**内存代价可接受**，且与 A 互不冲突。

### 6.4 对 H1c 的修正：10.6% 站不住

F1 的 10.6% 是这样推的：`7.06 ns × 假设每次乘法都付延迟`。F2 现在把假设测掉了：

- 真实乘法次数 = **1.076 亿**（不是 F1 反推的 53 M——F1 用延迟 21.73 ns 去除总时间，
  而真实均价是 10.70 ns，**差 2 倍**）；
- 真实均价 10.70 ns 已接近全内联吞吐 10.14 ns ⇒ **调用开销大部分被 ILP 掩盖**，
  剩下的空间只有 `10.70 − 10.14 = 0.56 ns/次`；
- 现实上限：`107.6 M × 0.56 ns ≈ 0.06 s`，即**约 1.8%**，而非 10.6%。

这不代表 H1c 是错的，而是它的**收益依据不成立**。若仍要验证，LTO 实验的价值在于
"确认没有隐性回退"，而不是期待两位数收益。**优先级应让位于杠杆 A。**

## 7. 对任务书三个"不能直接下结论"的回应

| 任务书要求谨慎的地方 | F2 给出的事实 |
|---|---|
| 不要因为 33% 就假定改底层算术能省 33% | 成立且更强：那 33% 里 38.4% 是"乘以 −1"，与 Montgomery 归约无关 |
| 0.6.1 asm 组的 −19.2% 不能全归因手写汇编 | 同一逻辑：prover 的真实形态是 10.70 ns，已在吞吐区间，汇编带来的空间比微基准显示的更小 |
| H1c 的 10.6% 只是理论上限 | 已证伪为高估，现实上限 ≈1.8%（§6.4） |

## 8. 局限

1. **`ConstantTerm` 的处理未单独计价**：2198 个常数项节点走 `B::constant_term`，
   内部生成低次多项式，成本与 `poly_len` 成正比但不在"整块乘法"里。它是残差的一部分。
2. **单价用的是 F1 的独立微基准**，不是本进程内实测；两者形态（流式 vs 分配-释放）不同，
   残差 0.12 s 就是这部分差异。
3. **CSE 收益是全树口径**，不区分"跨门共享"与"门内共享"；跨 instance 的门块结构相同但叶子
   索引不同（advice coset 不同），**不可共享**，这部分没有被夸大。
4. **8P 的隔离计时离散 15.7%**（424.4 ms，min 385.4 / max 449.9），单点不足以支撑强结论；
   但节点计数与 1P 逐位相同，说明并行只改 chunk 几何，不改工作量。
5. **只覆盖 V3 / 2 Action / K=11**。换 Action 数会改变 instance 数（门块重复次数），
   结构结论需要重测——这正是 F2 插桩保留在仓库里的原因。

## 10. 给 Stage F3 的建议

按"证据强度 × 改动面 × 可证明等价"排序：

| 优先 | 候选 | 收益上限 | 改动面 | 风险 |
|---|---|---:|---|---|
| **1** | **`Negated` 不再编译成 `Scale(−1)`** | **12.6%** | `Ast` 加一个变体 + 求值分支 | 极低，语义可逐项证明等价 |
| 2 | 叶子 chunk 缓存 | 3.6% | `recurse` 的 `Poly` 分支 | 低，但增加常驻内存 51 MB |
| 3 | H1c（LTO / 内联） | **≈1.8%**（原估 10.6%） | 编译配置 | 低，但收益依据已被削弱 |
| 4 | 选择性 CSE | ≤10%，需实测 | 求值器重构 | 高（内存 606 MB 全量不可行） |

**不建议**在 F3 阶段动 Montgomery 归约或 FFT：F2 已经把 quotient 的 89.1% 定位到求值器，
而求值器里最大的单项与域算术无关。
