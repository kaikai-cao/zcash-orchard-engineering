## 2. 改了什么

补丁 [`halo2_proofs-0.4.0-h7-borrowed.patch`](../experiments/transaction_e2e/vendor/halo2_proofs-0.4.0-h7-borrowed.patch)，
`+979/−52`，10 个 hunk，三个文件：

| 文件 | 行数 | 内容 |
|---|---:|---|
| `src/f3h7.rs` | +428 | 新增：五个分配点的计数器 + 写法微基准（`ORCHARD_H7` 门控，默认空转） |
| `src/lib.rs` | +3 | 模块声明 |
| `src/poly/evaluator.rs` | +548/−52 | 其中 **测试 +349**，**行为改动约 199 行** |

行为改动只有四处：

```rust
enum EvalValue<'a, F> { Borrowed(&'a [F]), Owned(Vec<F>) }   // 1. 返回值二态

impl BasisOps for {Lagrange,ExtendedLagrange}Coeff {         // 2. 借用路径
    fn get_chunk_ref(..) -> Option<&'a [F]>                  //    只有零旋转给 Some
}

fn recurse(..) -> EvalValue<'_, F> {                         // 3. 重写：四条纪律
    Ast::Poly(leaf)  => borrow_or_copy,
    Ast::Add | Mul   => 有一侧 Owned 就就地累加（可交换则交换左右），两侧都借才 collect,
    Ast::Scale | Neg => 子节点 Owned 就就地，否则 collect,
    Ast::DistributePowers => 单个 Owned 累加器,
}

out.copy_from_slice(root.as_slice())                          // 4. 根仍然拷贝一次（本轮不优化）
```

三条边界照预注册执行，一条没扩：**没有对象池、没有两段借用、根没有直写**。

## 3. 正确性（H7-A）

### 3.1 逐元素差分

参照实现是**旧的 `recurse` 逐行抄下来的**（叶子一律拷贝、每个节点改左子树那块缓冲区），
所以这个测试问的是"新旧是否逐位相同"，不是"新的看起来对不对"。

| 用例 | 覆盖的 ownership 分支 |
|---|---|
| `leaf` / `leaf@rot+1` / `leaf@rot−1` | 借用 / 拷贝 |
| `add/leaves` | 两侧都借 → `collect` |
| `add/borrow+own`、`add/own+borrow` | `reuse_left` 与 `reuse_right`（交换操作数） |
| `mul/leaves`、`mul/left-chain`、`mul/right-chain` | 同上，乘法的交换律 |
| `scale/leaf`、`scale/subtree` | 一元节点的两种来源 |
| `neg/leaf`、`neg/subtree`、`neg/scaled` | H6 的 `Neg` 与新路径的交叉 |
| `linear`、`constant`、`distribute` | 填充类节点与累加器 |
| `mixed-rotations`（`[0,+1,0,−1]`） | 借用的和拷贝的叶子在同一棵树里交错 |
| `deep`（15 节点、全类型、`rot ∈ {0,+1,−1}`） | 商表达式的真实形状 |

外加两个专项：

- `borrow_equals_copy_for_the_identity_rotation`：`k ∈ {5,6,7}` 的**每一个 chunk**
  （含最后一个短 chunk）上，借用窗口与 `get_chunk_of_rotated` 的拷贝逐位相同；
  非零旋转必须返回 `None` 而不是一个错的窗口。
- `operand_order_is_bit_identical`：`a + sub` 与 `sub + a`、`a * sub` 与 `sub * a`
  逐位相同——交换操作数这条捷径是唯一一处"看起来会改变求值顺序"的改动，单独钉住。

`cargo test --lib` → **45 passed / 0 failed**（H6 的 41 条 + 本轮的 4 条函数、22 个差分求值）。

### 3.2 真实电路

| 数据集 | 运行数 | 结果 |
|---|---:|---|
| D1（`--mode v3`） | 52 | 每次 `verify_proof` 通过（orchard + ironwood） |
| D2（`ORCHARD_E2_TIMING=1`） | 20 | 同上 |
| D3（`--mode f2`） | 24 | 同上 |
| D4（`--mode h7`） | 6 | 同上 |
| 合计 | **102** | 全通过 |

### 3.3 比"验证通过"更强的一条

同一个二进制、同一个 seed、计数开/关，**proof 指纹逐位相同**：

```
probe off  1P  0xa6bcd171d69e969a
probe on   1P  0xa6bcd171d69e969a   (×2)
probe off  8P  0xa6bcd171d69e969a
probe on   8P  0xa6bcd171d69e969a   (×2)
```

而这个值**等于 H6 冻结时的记录**（文档 18 的惰性对照用的就是它）。也就是说：
H6 → H7 这一步改变了分配结构、改变了 6100 块缓冲区的来源，但**没有改变任何一个域元素**。
"验证通过"对某些 bug 也会通过，逐位相同不会。

种子固定时证明是确定的，所以这条可以作为 A/B 的正确性对照——但按用户的要求，
**没有把 A/B 的 proof 字节当作验收指标**，它只在这里作为"改动是纯实现层面"的证据出现。

## 4. 机制（H7-B / H7-C）：谁在分配

`--mode h7`，融合树那一次 `evaluate`，`poly_len 16384`：

| 量 | A（每叶子拷贝） | B（借用） | Δ |
|---|---:|---:|---:|
| 叶子访问（4 chunk） | 18528 | 18528 | 0 |
| └ 借用 | 0 | **16064**（86.70%） | |
| └ 拷贝 | 18528 | **2464**（13.30%） | |
| 叶子拷贝字节 | 2.4285 GB | **0.3234 GB** | **−86.70%** |
| 分配次数 | 27444 | **21316** | **−22.33%** |
| 分配字节 | 3.5971 GB | **2.7939 GB** | **−22.33%** |

**两条不变量逐位闭合**（探针里直接 assert，报告里打 `closed_leaf` / `closed_alloc`）：

```
borrowed + copied == leaf_visits            16064 + 2464 = 18528   ✓
allocs == copied + fills + both_borrowed + unary
         2464 + 8916 +  1288     +   8648   = 21316              ✓
```

`leaf_visits / 4 = 4632` 与 F2 独立数出来的 `ast.poly` 逐位相同——**两次独立的树遍历互证**。

### 4.1 少掉的 1532 次分配在哪

按每 chunk 归一（×4）：

| 归属 | 次/chunk | A 的代价 | B 的代价 |
|---|---:|---|---|
| 借来的叶子，父节点已经有缓冲区 | **1210** | 1 次拷贝 | **0**（这是真省下的） |
| 借来的叶子，父节点是 `Scale`/`Neg` | 2162 | 1 次拷贝 | 1 次乘积写入（**不是优化，只是不再叫拷贝**） |
| 借来的叶子，成对进入二元节点 | 644 → 322 | 2 次拷贝 | 1 次 `collect`（**省一半**） |
| 非零旋转，必须物化 | 616 | 1 次拷贝 | 1 次拷贝（不变） |
| 常量 / 线性项填充 | 2229 | 1 次填充 | 1 次填充（不变） |

```
4632 − (1210 + 322 + 616) = 2484 ... 
A: 4632 + 2229 = 6861        B: 616 + 322 + 2162 + 2229 = 5329       差 1532 ✓
```

**"省下的"只有 1210 + 322 = 1532 次**，占 A 的 22.3%。这正是 H7-B 字面失败的地方：
我当初按"4016 次都白拷贝了"估，写了个"分配字节 ≤ 70%"（即 ≥30% 的降幅）；
真实情况是 4016 次里有 2162 次本来就要写一块缓冲区（`Scale`/`Neg` 必须有输出），
只是这块缓冲区以前叫"拷贝"、现在叫"乘积"。

### 4.2 换线程数不变

8P（`chunk 512 × 32`）的总量与 1P 完全相同（18528 / 16064 / 2464 / 21316 / 2.7939 GB），
只有分配的分段不同（fills 71328 vs 8916 等）。**分块策略不改变账本**，这一点本身就是
"计数不是被分块方式凑出来的"的证明。

## 5. 价格（D4）：同一件事的两种写法值多少钱

`ORCHARD_H7_BENCH=7`，单线程，在两个几何上各测三种写法（ns/元素）：

| 几何 | 拷贝+就地乘 | `collect(zip)` 乘 | 只拷贝 | 比值 |
|---|---:|---:|---:|---:|
| **chunk 4096**（`recurse` 的真实单位，128 KiB） | 14.289 | **12.287** | **0.499** | 1.163 |
| **poly 16384**（LC 的口径，512 KiB） | 16.209 | 17.215 | **1.223** | 0.942 |

三件事：

1. **拷贝的价格强烈依赖缓冲区大小**：128 KiB 时 0.499，512 KiB 时 1.223，LC 去年测到 1.4814。
   原因是缓冲区一大就离开 L2，读的是散在 72.5 MiB 工作集里的多项式。
2. **在真实粒度上 `collect` 确实更便宜**（12.287 vs 14.289，省 14%），
   但到 512 KiB 上反而更贵（17.215 vs 16.209）——所以 H7 的收益主要不是"写法更快"，
   而是"这件事根本不用做"。
3. LC 的 1.48 是**冷口径**。用它推 H7 的收益，等于用"缓存未命中时的拷贝价格"
   去乘"缓存命中时发生的拷贝次数"。

### 5.1 反解现场价格

用 D3 的实测降幅除以去掉的元素数：

```
1P 求值器 Δ = 1125.0 − 1174.3 = −49.3 ms
去掉的拷贝 = (4632 − 616) × 4 chunk × 4096 元素 = 65.8 M 元素
现场价格 = 49.3 ms / 65.8 M = 0.749 ns/元素
```

对照三个估计：

| 口径 | ns/元素 | 推出的收益 | 与实测 49.3 ms |
|---|---:|---:|---:|
| 孤立 · chunk 128 KiB（本轮 D4） | 0.499 | 32.8 ms | 低估 1.5× |
| 孤立 · poly 512 KiB（本轮 D4） | 1.223 | 80.5 ms | 高估 1.6× |
| 孤立 · LC 2026（1.4814） | 1.4814 | 97.5 ms | 高估 2.0× ← 预注册用的就是这个 |
| **现场（由 D3 反解）** | **0.749** | — | — |

**两个孤立基准把真值夹在中间，真值偏冷的那一侧。** 这解释了 P3 为什么错：
我把"冷价格"当成了"边际价格"。

这里数的是**搬运遍数**（一个拷贝当量 = 读一遍 + 写一遍 128 KiB），不是缓冲区个数。
两者不矛盾：2162 个 `Scale`/`Neg` 仍然要写一块输出，但少了"先把叶子拷出来、
再读这块拷贝"的一读一写，所以照样省下一整个拷贝当量。§4.1 数的 1532 是**缓冲区个数**
的净减少，回答的是"少了多少次分配"；这里回答的是"少搬了多少字节"。

## 6. 三层传递：这次是 105%

| 层 | A | B | Δ | 95% CI |
|---|---:|---:|---:|---|
| 求值器（D3，1P） | 1174.3 ms | **1125.0 ms** | **−3.28%** | [−7.74, +1.59] |

## 9. 这几道门为什么"字面失败"，其中四处是我预注册写错了

### 9.0 先说不失败的

H7-A（正确性）与 H7-C（分配次数不增加、峰值内存不增）都是干净的通过，没有任何折扣。
下面四道是字面失败的，逐条说明原因；**判据一个都没有事后调整，只解释它测到了什么。**

### 9.1 H7-B（分配字节 −22.3%，阈值是"≤ 70%"）

**阈值是拍的，不是推的。** 预注册里没有写这个 70% 从哪来——它是"大部分拷贝都会消失"
这个直觉翻译成的数字。实测 22.3% 是这件事的真实上限（§4.1 的分解是精确的）。
按字面 FAIL，按意图（拷贝大幅下降、分配次数不增加）通过。**两句话都写在这里，不合并。**

### 9.2 H7-D（求值器 ≥ 5%）

**这个门槛写下来时就不可能过。** 它隐含地要求"求值器降幅 ≥ 5%"，而 5% 的来源是
`112.4 ms / 1144.7 = 9.8%` 这个 LC 口径的份额——一旦价格从 1.48 修正到 0.75，
上限就是 `0.75/1.48 × 9.8% = 4.8%`。**门槛本身用错了输入，所以它测的不是假设，是我的算术。**

### 9.3 H7-F / H7-G（8P 与其它阶段的 CI 上限 ≤ +1%）

8P 的组内 CV 是 8.2% / 7.3%，26 对配对的 CI 半宽约 ±3%——**要求 ±1% 的分辨率，
样本量差一个数量级**。这两条门槛把"点估计"和"CI 上限"混在一起，而后者在这个噪声下永远过不了。
按字面 FAIL，实际信息量是"点估计没退化（+0.18%）"。

顺带一个场外事实：本轮 8P 的 A 侧中位数 **908.0 ms**，比 H6 记录的 784.8 ms 高 15.7%，
CV 也从 3% 上下变成 8%。这台机器今天的 8P 臂明显更吵，这也是 CI 变宽的直接原因。

### 9.4 H7-H（决定规则本身不完备）

我写的是："A ∧ B ∧ D ∧ E → 保留；D 过而 E 不过 → 记收益不传递并关档；D 不过 → 关档。"
**没有写"B 或 D 不过、但 E 过"这一支**——而这正好是今天的结果。规则不完备是预注册的缺陷，
不是结果的缺陷。§10 给出按字面与按工程门槛的两个答案，并把选择权交回。

## 10. 决定：保留补丁，关闭 H7.5

**按 H7-H 的字面：关档**（D 不过）。**按 H7-E（写在数据之前的工程门槛）：−1.45%，
CI 排除零，过。** 两条都成立，因为 H7-H 把"幅度假设"（D）当成了"留不留"的裁判。

我的建议是把两件事分开：

| 问题 | 答案 |
|---|---|
| 这个补丁值不值得留在树上？ | **值**。−1.45% 是显著的、可复现的、机制可对账到字节的，且没有任何阶段退化（除 0.14% 的布局噪声）。 |
| 还值不值得继续投 H7.5（池化 / 两段借用 / 根直写）？ | **不值得**。三项的合计上限可以算出来： |

```
两段借用（剩下的 13.3% 拷贝） 2464 块 × 128 KiB × 0.75 ns/元素 → 7.5 ms = 0.27%
根直写                        4 chunk × 4096 元素 × 0.75 ns    → 0.012 ms ≈ 0%
池化（省 malloc 调用，不省字节） ≤ 6128 次 × ~0.1 µs            → 0.6 ms = 0.02%
                                   合计上界 ≈ 0.29% 的完整证明
```

**0.29% 的上界，换整个缓冲区纪律的复杂度，不划算。** H7 已经把它能拿的都拿了，
剩下的边际收益落在工程噪声里。

预注册 §7 里估的两段借用"15 ms / 0.5%"偏低，按本轮现场价格应为 7.5 ms / 0.27%——
这里更正方向（不是更正判据）。

### 10.1 下一步：登记 H8，不动代码

H7 之后，**剩下的最大一块物化成本不是叶子，是常量**：

```
B 侧每次求值的 2.794 GB 分配字节里（每块缓冲区恒为 4096 × 32 B = 128 KiB）：
  常量 / 线性项填充   1.169 GB   41.8%   8916 块   ← 最大的一块
  Scale / Neg 输出    1.133 GB   40.5%   8648 块
  叶子拷贝（rot≠0）    0.323 GB   11.6%   2464 块
  二元节点 collect    0.169 GB    6.0%   1288 块
```

8916 块常量缓冲区，每块只是 `[scalar; 4096]`。`Ast::ConstantTerm` 在融合树里有 2198 个
（每 chunk 归一），绝大多数来自门表达式里的 `Expression::Constant(q_c)`。

**H8 的形态**（未开工，需要独立预注册）：

- `Add(ConstantTerm(c), x)` 不必物化一块缓冲区，只需对每个元素加一个标量；
- `ConstantTerm(0)` 若存在，`Add(0, x)` 与 `Mul(1, x)` 可以整棵剪掉；
- 上界 = 那 1.169 GB 的填充本身。按本轮反解的现场拷贝价格 0.75 ns/元素折算，
  36.5 M 元素 × 0.75 ns = **27 ms ≈ 1.0% 的完整证明**；纯写比"读+写"便宜，
  所以实际更低。注意它**不**省后面的加法遍——`Add(Constant(c), x)` 仍要对每个元素加一个标量，
  只是不再先造出一块全是 `c` 的缓冲区。

但**先要回答两个问题才值得开工**（与 LC 的教训一致）：
① 2198 个常量里有多少是 0（也就是有多少是真的可剪）；
② `ConstantTerm` 在树里出现在什么位置（累加器位置 = 只能省填充，只读位置 = 连接口都能省）。
两个都能用一次零改动的普查回答，不需要先写优化。

## 11. 方法论：第三次"孤立价格 ≠ 现场价格"

三次都栽在同一处，方向不同，教训是同一条：

| 轮次 | 用了什么价格 | 错在哪 | 幅度 |
|---|---|---|---|
| H6 · P2 | 微基准吞吐（11.2 ns/乘） | 真实循环里乘法在依赖链上，移除它的收益**大于**吞吐占比 | 预测 8–20%，实测 31.5% |
| LC | 全向量拷贝（1.48 ns/元素） | 那是 **72.5 MiB 工作集**下的冷价格 | 数值准，但用错了对象（不是"可避免"的部分） |
| **H7 · P3** | 同一个 1.48 ns/元素 | 同上：`recurse` 的单位是 128 KiB，不是 512 KiB | 预测 −8.5%，实测 −3.3% |

**规则**：一个"ns/元素"只在它被测量的那个缓冲区大小 + 工作集下成立。
要预测一个改动值多少，要么在**同样的粒度**上测，要么给出上下界并说明真值落在哪一侧。
本轮的 D4 做到了后者：0.50 与 1.22 夹住 0.75，而 0.75 是反解出来的——**这才是可用的预测区间**。

顺带一条：**结构可预测，价格不可预测。** 四轮下来，凡是"节点数 / 访问次数 / 字节数"
的预测全部逐位命中（P1 三次全中），凡是"多少毫秒"的预测只有一次落在区间内（H6-P4）。
这不是巧合：前者由代码结构决定，后者由微架构和缓存状态决定。
